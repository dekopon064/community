# 운영자 접근 제어 설정

이번 구현은 앱의 운영자 접근 제어만 제공합니다. review 목록·편집·승인·반려·게시 기능과 DB RPC 실행 권한은 아직 연결하지 않았습니다.
Google 로그인 및 실제 OAuth 확인은 사용자가 완료했다고 알려 주었습니다. 아래 운영자 접근 기능의 에이전트 검증은 로컬 가짜 인증 환경입니다.

## 운영자 UUID 등록

1. 로그인에 사용하는 Supabase 프로젝트에서 Authentication → Users를 엽니다.
2. 운영자로 지정할 계정을 선택하고 해당 사용자의 ID(UUID)를 확인합니다.
   Google Cloud 프로젝트 ID, OAuth Client ID, 이메일과는 다른 값입니다.
3. 현재 작업 폴더 `.worktrees/google-login`의 Git에서 제외되는 `.env.local`에 다음 서버 전용 변수를 추가합니다.
   기존 Google·Supabase·문의 화면 설정은 유지하세요.

```dotenv
MACHIMOA_ADMIN_USER_IDS=<운영자-사용자-UUID>
```

여러 명은 `<첫번째-UUID>,<두번째-UUID>`처럼 쉼표로 구분합니다. 위 예시의 꺾쇠·설명 문구 대신 실제 UUID만 입력합니다.
`NEXT_PUBLIC_` 접두사를 붙이지 않습니다. 실제 UUID는 이 문서나 코드에 넣지 않습니다.
허용 목록이 비어 있으면 운영자가 없습니다. 잘못된 UUID 또는 빈 쉼표 항목이 하나라도 있으면 목록 전체를 무효로 처리합니다.

4. 실행 중인 개발 서버를 종료하고 기존과 같은 포트로 다시 시작합니다.
   `npm run dev -- --port 3100`
5. 일반 Chrome/Edge에서 `http://localhost:3100/ko/admin`에 접속합니다.
   로그아웃 상태이면 Google 로그인 화면으로 이동하며 로그인 후 관리자 경로로 복귀합니다.
6. 지정된 계정은 접근 확인 완료 화면을, 다른 계정은 접근 제한 안내를 받아야 합니다.
   `/ja/admin`은 한국어 관리자 경로로 이동합니다.

실제 운영자 확인에는 지정 계정과 일반 계정을 따로 시험하세요. 로그아웃 또는 별도 브라우저 프로필을 사용할 수 있습니다.
비밀값·인증 토큰을 채팅에 붙여 넣을 필요는 없습니다. 설정 파일은 이번 작업에서 수정하지 않았습니다.

## 서버 적용 지점

- `app/lib/auth/admin.ts`: 서버 전용 환경변수를 읽고 요청별 Supabase Auth 클라이언트를 생성합니다.
- `getAdminAccess({ readOnly: true })`: 페이지에서 접근 상태를 판정합니다. 페이지 쿠키 갱신은 기존 Proxy가 담당합니다.
- `requireAdmin()`: 이후 Route Handler / Server Action에서 보호 데이터 조회·mutation 이전에 호출합니다.
  허용되지 않으면 예외를 던지므로 작업이 계속 실행되지 않습니다. 반환하는 `userId`는 서버에서 검증한 JWT의 `sub`입니다.
- `app/lib/auth/admin-policy.ts`: UUID 목록 검사, 검증된 사용자 대조, 차단 오류를 정의합니다.
  순수 정책 자체는 테스트할 수 있지만, 실제 앱 호출은 서버 전용 adapter를 통과합니다.
- `GET /api/admin/access`: 같은 `requireAdmin()`을 사용하는 최소 권한 확인 경로입니다.
  UUID·목록·토큰을 반환하지 않고, 미로그인 401 / 일반 사용자 403 / 인증·설정 실패 503 / 운영자 200을 반환합니다.

검사는 요청마다 수행합니다. 클라이언트 UUID·이메일·프로필의 `admin` 값으로 권한을 얻을 수 없습니다.
Proxy는 세션 갱신과 캐시 차단을 담당하며 유일한 권한 검사 지점으로 사용하지 않습니다.
관리자 페이지의 제한 안내는 정보성 화면이며 HTTP 200으로 렌더링될 수 있습니다. 보호된 서버 API의 거부는 위의 HTTP 상태로 구분합니다.

## DB 권한의 별도 경계

이 저장소 main에서 읽은 계약상 `machimoa_review.publish_curation_candidate`는 public / anon / authenticated / service_role에
실행 권한을 주지 않습니다. 앱 허용 목록에 UUID를 넣어도 이 DB 권한이 변경되지는 않습니다.
현재 앱에는 review 관리자 mutation 경로가 없습니다.

다음 단계에서 필요한 작업은 운영자 서버 검사 이후 호출할 제한된 DB/RPC 경로, 승인자 UUID 기록,
revision 충돌 검사와 저장·게시 이력을 함께 설계하는 것입니다. 이번에는 DB 연결이나 권한 변경을 수행하지 않았습니다.

## 로컬 시험

`npm run test:auth`는 실제 Supabase SSR SDK와 루프백 가짜 Auth 서버를 사용합니다.
운영자 UUID 대조, 여러 UUID·중복·공백, 비어 있거나 잘못된 목록, 인증 실패, 위조 프로필·토큰,
차단 후 보호 작업 미실행, HTTP 차단 상태와 no-store 헤더 및 기존 Google 로그인 기반을 시험합니다.

로컬 브라우저용 `node scripts/test_auth.mjs --serve`의 계정은 가짜 시험 계정입니다.
이를 실제 Google OAuth 또는 실제 운영자 확인으로 해석하지 마세요.
